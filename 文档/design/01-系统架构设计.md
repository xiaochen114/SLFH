# 异构多机器人中央调度系统 · 架构设计

> 版本：v1.0 | 日期：2026-06-07
> 设计原则：中央大脑调度 + 末端自主决策 + 统一接口标准化

---

## 1. 核心理念

```
一套通用的"中央大脑 + 异构机器人"调度系统架构
↓
森林防火作为第一个落地场景来验证
↓
未来可扩展到安防、搜救、农业等场景
```

**关键词：** 大模型调度、异构统一接口、通信自适应、边缘自主

### 2.1 中心层（中央大脑）

| 模块 | 职责 | 技术选型 |
|------|------|---------|
| LLM 调度引擎 | 接收末端上报信息，做决策（派单、调路线、研判火情） | DeepSeek API / 通义千问 API |
| **机器人运维 Agent** | **远程诊断末端软件问题：SSH登录、查日志、重启服务、修复配置、异常恢复** | **Python + SSH + agent 脚本** |
| 任务规划器 | 把 LLM 决策转为具体任务（巡逻路线、目标点） | Python 规则引擎 + LLM 混合 |
| 机器人注册中心 | 管理在线设备列表，记录能力/位置/电量 | Python dict + JSON 持久化 |
| 人机交互面板 | 地图展示、状态监控、手动干预 | Flask + Web (已有) |
| 通信管理器 | 统一收发、自动检测连接状态、缓存离线消息 | Python asyncio + 队列 |

**工作流：**
```
末端上报事件 → LLM 研判 → 规划器生成任务 → 下发末端 → 末端执行并反馈
```

### 2.2 中间层（通信抽象）

```
┌──────────────────────────────────┐
│      通信抽象接口                 │
│  .connect()                      │
│  .send(robot_id, msg)            │

│  .get_quality() → 信号质量       │
└──────┬──────┬──────┬────────────┘
       │      │      │
  ┌────┴──┐ ┌┴───┐ ┌┴─────┐
  │ WiFi  │ │ 4G │ │ Mesh  │
  │ 驱动   │ │ 驱动│ │ 驱动   │
  └───────┘ └────┘ └──────┘
```

**关键设计：** 中央大脑不直接处理具体通信协议，所有通信通过统一接口。机器人断连时消息自动缓存，重连后补发。

### 2.3 执行层（末端机器人）

每个机器人实现统一接口即可接入系统。

## 3. 核心创新：标准化机器人接口

### 3.1 接口定义

```python
class RobotBase(ABC):
    """所有机器人必须实现的基类"""

    # === 基本信息 ===
    @property
    def robot_id(self) -> str: ...
    def get_capabilities(self) -> list: ...  # ['move','camera','detect','audio']

    # === 生命周期 ===
    @abstractmethod
    def connect(self) -> bool: ...
    @abstractmethod
    def disconnect(self): ...
    def is_connected(self) -> bool: ...

    # === 控制指令（统一接收，内部转换） ===
    @abstractmethod
    def execute_order(self, order: RobotOrder) -> OrderResult: ...

    # === 状态上报 ===
    @abstractmethod
    def get_status(self) -> RobotStatus: ...

    # === 边缘自主（可选，但建议实现） ===
    def on_communication_lost(self): ...   # 断网时自动降级
    def on_communication_restored(self): ... # 恢复后同步

@dataclass
class RobotOrder:
    order_id: str
    type: str            # 'patrol' / 'inspect' / 'alert' / 'return' / 'custom'
    params: dict         # {'target': [x,y], 'speed': 1.0, ...}
    priority: int        # 0=低, 1=中, 2=高, 3=紧急

@dataclass
class RobotStatus:
    robot_id: str
    position: tuple     # (x, y, yaw)
    battery: float      # 0.0~1.0
    mode: str           # 'idle' / 'patrolling' / 'alert' / 'returning'
    health: str         # 'ok' / 'warning' / 'error'
    extra: dict         # 各机器人特有的状态
```

### 3.2 接入新机器人只需：继承 RobotBase + 实现抽象方法

```
只要有新设备，写一个类继承 RobotBase，然后注册到中央大脑。
中央大脑不需要知道你是机器狗还是无人机还是扫地机。
```

## 4. 中央大脑 LLM 调度流程

```
事件触发 ──→ LLM 评估 ──→ 规划器分解 ──→ 下发末端 ──→ 反馈闭环
```

### 4.1 典型流程举例

```
1. 机器狗: "报告，发现疑似烟雾，位置(120, 85)"
2. 中央 LLM: "研判：置信度0.7，需要无人机复核。命令：无人机飞到(120,85)拍照，
   机器狗继续前进到(150,80)扩大观察"
3. 规划器: 拆成 → [无人机的飞行路径] + [机器狗的巡逻路径]
4. 下发 → 各自执行
5. 无人机: "已到达，高空红外未发现异常" 或 "红外发现热点，确认火情"
```

### 4.2 LLM 接入设计（API 调用）

```python
class LLMEngine:
    """大模型调度引擎 - 统一接口，可切换不同模型后端"""

    def __init__(self, provider: str):
        # provider = 'deepseek' / 'qwen' / '本地ollama'
        ...

    def decide(self, context: dict) -> Decision:
        """
        输入：全局状态（各机器人状态 + 检测事件 + 通信质量）
        输出：决策指令
        """
        prompt = self._build_prompt(context)
        response = self._call_llm(prompt)
        return self._parse_decision(response)
```

## 4.3 机器人运维 Agent

中央大脑内置一个专门负责末端设备软件运维的 Agent，通过 SSH 远程连接机器狗/无人机的机载电脑（Jetson），执行诊断和修复操作。

**典型场景：**

| 问题 | Agent 响应 |
|------|-----------|
| 机器狗 YOLO 检测掉线 | SSH 登录检查 `systemctl status transfer` → 重启服务 |
| 摄像头无画面 | 检查 `realsense-viewer` 进程 → 重启相机驱动 |
| Jetson 磁盘满 | 清理 `/var/log` 旧日志 → 报磁盘使用率 |
| 机器狗状态异常 | 拉取 `/jy_exe/data` 故障日志 → 分析根因 → 恢复 |
| 网络模块不响应 | ping 测试 → 重启网络服务 → 重新注册 |

**设计：**

```python
class RobotOpsAgent:
    """运维 Agent - 远程诊断和修复末端软件问题"""

    def __init__(self):
        self.ssh_conns = {}  # robot_id -> paramiko client

    def diagnose(self, robot_id: str, symptom: str) -> Diagnosis:
        """根据症状执行诊断流程"""
        checks = self._get_checklist(symptom)
        for check in checks:
            result = self._run_check(robot_id, check)
            if not result.ok:
                return self._repair(robot_id, result)
        return Diagnosis(ok=True)

    def _run_check(self, robot_id: str, check: str) -> CheckResult:
        """通过 SSH 在末端执行检查命令"""
        ssh = self._get_ssh(robot_id)
        stdout, stderr = ssh.cmd(check)
        return CheckResult(stdout, stderr)

    def _repair(self, robot_id: str, result: CheckResult) -> Diagnosis:
        """根据检查结果执行修复"""
        fix = self._match_fix(result)
        ssh = self._get_ssh(robot_id)
        ssh.cmd(fix)
        return Diagnosis(ok=True, action=fix)
```

**触发方式：**
1. **自动触发**：机器人状态异常（health=warning/error）或 LLM 调度中发现设备异常
2. **人工触发**：操作员在 Web 面板点击"诊断"按钮
3. **定时巡检**：Agent 定期对在线设备执行健康检查

**与 LLM 调度的关系：**
```
LLM 调度引擎  ←→  机器人运维 Agent
     ↓                    ↓
做"干什么"的决策      做"怎么修"的操作
```
两者配合：LLM 发现设备异常 → 通知运维 Agent 诊断修复 → 修复完成后通知 LLM 继续调度。

## 5. 末端边缘自主设计

### 5.1 三级自主决策

| 级别 | 通信状态 | 决策方式 | 说明 |
|:----:|---------|---------|------|
| L1 | 在线 | 中央决策 | 正常模式，中央 LLM 全面调度 |
| L2 | 弱连接 | 混合决策 | 中央下优先级任务，末端执行细节。**系统优先保持在 L2** |
| L3 | 断连 | **边缘自主** | 末端按内置规则自主运行。紧急情况，**应尽快恢复至 L2** |

### 5.2 核心设计：断网主动恢复（L2 优先策略）

**关键设计思想：** 末端断连后，不等待其自行恢复，而是中央大脑主动派出无人机充当空中通信中继，尽量把断连设备拖回 L2。

```

断网检测 (3次心跳超时)
  ↓
中央大脑收到断连事件
  ├─ 记录断连设备最后已知位置 (x, y)
  ├─ 检查是否有可用无人机
  │    ├─ 有 → 派遣无人机飞至断连设备上空
  │    │       └─ 无人机作为空中 WiFi 热点 / Mesh 中继
  │    │       └─ 目标：恢复连接 → 回到 L2
  │    └─ 无 → 通知地面站，等待自动重连
  │
  ├─ 末端侧同时进入 L3 自主模式
  │    ├─ 继续按最后一次下发的巡逻路径巡逻
  │    ├─ YOLO 检测正常运行
  │    ├─ 发现火情：自动急停 + 记录GPS + 持续尝试上报
  │    └─ 超声波避障正常运行
  │
  └─ 网络恢复（通过无人机中继或自行重连）
       ├─ 补发离线期间的日志和检测记录
       └─ L3 → L2（无人机中继维持弱连接）或 L1（完全恢复）
```
